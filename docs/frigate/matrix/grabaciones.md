## Hallazgos de RBAC y exposición (sin consolidar; ver la matriz principal)

- ALTA: acceso cruzado entre canales mediante playbackURI, vigente en esta rama. POST /api/recordings/playback y POST /api/recordings/preview/start aceptan playbackURI (z.string().startsWith('/')) y le inyectan usuario y contraseña del NVR sin comprobar que la pista pertenezca a camera.channel. Un AUDITOR con canPlayback en una sola cámara puede pedir la pista de otra cámara del mismo NVR, o cualquier otra ruta RTSP del NVR. También puede entrar en el plan de intentos (nvr_*). Evidencia: apps/api/src/routes/recordings.ts:1324-1338, :1600-1627, :2014-2045, :2145; apps/api/src/services/recordings/rtsp-url.ts:228-242, :368-386. La corrección es #186 ((rama de #186) apps/api/src/services/recordings/playback-uri-policy.ts:1-15, usada en wtsec recordings.ts:1613 y :2038) y no está en docs/frigate-native-plan.
- MEDIA: la descarga no respeta la política de permisos declarada. Las plantillas de rol niegan canDownloadRecordings a SUPERVISOR y AUDITOR (apps/api/src/services/totp.ts:103-125), y existe canDownload por cámara (prisma/schema.prisma:294), pero routes/recordings.ts no lee ninguno: POST /playback y GET /download quedan abiertos a SUPERVISOR y a AUDITOR con canPlayback (recordings.ts:1590-1605, :1908-1979). La web muestra «Generar MP4…» sin comprobar nada (RecordingsPage.tsx:2843-2878). docs/security/USER_PERMISSIONS_MATRIX.md:66 y :92 los clasifican como SUPERSEDED por authorize(['ADMIN']) en recordings.ts:1976, pero esa protección corresponde a GET /audit (hoy :1982).
- MEDIA: no hay revocación para grabaciones. Al cambiar permisos (POST /api/users/:id/permissions) solo se revocan los media-grants y los WebSockets (users.ts:451-477). Las previews (TTL de 30 min) y los trabajos VOD siguen vivos, y los tokens de /stream, /file.mp4 y /download (24 h) siguen sirviendo porque esas rutas solo validan el token (recordings.ts:43-44, :1829-1837, :1908-1925, :2288-2297). El DownloadToken no guarda userId ni cameraId, así que no se puede revocar por usuario (recordings.ts:285-292).
- MEDIA: el rol y el estado activo se leen del JWT sin consultar la base. authenticate y authorize solo verifican la firma (apps/api/src/plugins/auth.ts:78-127; expiresIn 60m por defecto, :66). Un SUPERVISOR degradado a OPERATOR o desactivado conserva el acceso sin filtro a /api/recordings/* hasta que vence el token (recordings.ts:1410, :2005). Quitar canPlayback a un AUDITOR sí rige en la siguiente solicitud, porque se consulta la base en cada una.
- BAJA: huecos de auditoría. El acierto de caché de POST /playback emite el token de descarga sin AuditAction (recordings.ts:1676-1706, frente a :1776). GET /download solo deja log (:1908-1979). GET /calendar no audita (:1451-1494). La captura PNG no se registra (RecordingsPage.tsx:2203-2232).
- BAJA: la UI no coincide con la API. El botón Revalidar del banner de /recordings se muestra a AUDITOR y responde 403 (RecordingsPage.tsx:2483-2494; nvr.ts:1371). En /nvrs/:id el mismo botón es solo ADMIN aunque la API acepta SUPERVISOR (NVRDetailPage.tsx:1822). /nvrs muestra Agregar, Editar y Eliminar a SUPERVISOR, pero la API es solo ADMIN (NVRsPage.tsx:357, :533-534; nvr.ts:1218, :1287, :1330). El audio por cámara está deshabilitado en la UI para SUPERVISOR y la API lo permite (NVRDetailPage.tsx:1310; cameras.ts:714), y ese cambio no se audita.
- BAJA: minimización de datos. GET /api/cameras y GET /api/cameras/:id devuelven nvr.ipAddress a usuarios con permiso de una sola cámara (cameras.ts:66, :108), mientras que GET /api/nvrs reduce la respuesta a id y nombre en ese caso (nvr.ts:309-322). El árbol de /recordings usa esa lista.
- BAJA: permisos de grabaciones que se aceptan pero no se aplican. canViewRecordings (feature y NVR) no se lee en ningún lado. El esquema de permisos por NVR no tiene canPlayback (users.ts:54-64), así que no hay forma de dar grabaciones a nivel de NVR. La lista de cámaras sale de canView y no de canPlayback (cameras.ts:62-68): un AUDITOR ve cámaras que responden 403. A un OPERATOR se le puede asignar canPlayback en /users, pero la API lo rechaza por rol (recordings.ts:1410).
- BAJA: GET /api/views y GET /api/views/:id devuelven a cualquier usuario con acceso a un visor público la lista de acceso con fullName y username de otros usuarios, y cameraSlots sin filtrar por permiso de cámara (views.ts:26-46, :49-72). - BAJA: oráculo de existencia. /search, /calendar, /playback y /preview/start responden 404 por cámara inexistente antes de verificar canPlayback, y /batch-search responde 404 por NVR o cámaras antes de filtrar (recordings.ts:1412-1415, :1462-1464, :1508-1514, :2009-2012).
