## Hallazgos de RBAC y exposición (sin consolidar; ver la matriz principal)

- CRÍTICO, confirmado por lectura y no ejecutado. Los tokens auxiliares se aceptan como credencial de acceso y abren las grabaciones de cualquier cámara. `authenticate` sólo llama a request.jwtVerify(), que valida firma y expiración de cualquier JWT firmado con JWT_SECRET y prioriza el header Bearer (plugins/auth.ts:63-96, comentario 68-70; @fastify/jwt ^10.1.0 en apps/api/package.json:20, lookupToken en node_modules/@fastify/jwt/index.js:258-264 v10.1.0). El API emite con la misma clave, y devuelve en el body, tres JWT sin `role`: tempToken {step:'2fa'} (auth.ts:163-168), enrollToken {step:'mfa-enroll'} (auth.ts:154-159) y stepUpToken {step:'elevated'} (auth.ts:411-413). Las rutas de grabaciones usan listas negras (`if role==='OPERATOR' → 403`, `if role==='AUDITOR' → canPlayback`), así que role=undefined sigue de largo, descifra la contraseña del NVR y busca o reproduce cualquier cámara. Ocurre en GET /api/recordings/search (recordings.ts:1406-1428), /calendar (1451-1470), POST /batch-search (1497-1522), /playback (1590-1612) y /preview/start (2003-2022). Hay tres vías. (a) Cualquier OPERATOR o AUDITOR logueado llama POST /api/auth/step-up (sólo authenticate, auth.ts:384-386) con su propia contraseña o TOTP y usa el token como `Authorization: Bearer`: escala a todas las grabaciones. (b) Quien conozca sólo la contraseña de una cuenta con 2FA usa el tempToken: evita el TOTP y obtiene grabaciones de todas las cámaras, el vivo de las cámaras del usuario (cameras.ts:51-72, 378), /api/auth/me y PUT /api/profile y /api/profile/password. (c) Un usuario con enrolamiento MFA pendiente usa el enrollToken (15 min). También se saltan las negaciones a AUDITOR de cameras.ts:124, 322 y 345. No hay pruebas con tokens sin rol: grep de 'elevated' o 'step-up' en *.test.ts no da resultados. Rompe el invariante 2.
- ALTO, confirmado por lectura. El refresh JWT funciona como access token por 7 días y no se puede revocar. Lleva {sub, username, role, jti}, está firmado con la misma clave y vence según JWT_REFRESH_EXPIRES_IN, 7d por defecto (auth.ts:632-636, 975-978). `authorize` lo acepta como Bearer sin consultar Session ni User (plugins/auth.ts:99-112). Un usuario que copie su cookie refresh_token (o access_token) desde su navegador conserva el acceso con su rol hasta 7 días, aunque lo desactiven, le bajen el rol, lo eliminen o le revoquen las sesiones (users.ts:244-275, 548-573; auth.ts:564-596, 709-746). Sólo /refresh y /ws-ticket verifican active o Session (auth.ts:626, 940-952).
- ALTO, confirmado por lectura. GET /api/auth/me expone datos del NVR y la cámara a usuarios no ADMIN y la web los guarda en localStorage. userMeSelect incluye `permissions: { include: { nvr: true, camera: true } }` (auth.ts:55-61, 907-921), así que a todo OPERATOR o AUDITOR con permisos le devuelve la fila completa del NVR: username, password cifrada, ipAddress, puertos y número de serie (schema.prisma:107-118). También la fila completa de la cámara, con su IP (schema.prisma:189). La web guarda ese objeto en localStorage 'visioncore-auth' en cada carga (App.tsx:30-33; authStore.ts:173-180, 223-228). Contradice el invariante 6. GET /api/users/:id ya hace bien el select acotado (users.ts:144-149).
- MEDIO. Las alertas de NVR llegan a todos los usuarios conectados por WebSocket. broadcastAlertScoped hace broadcast global cuando cameraId es null (websocket.ts:38-41), y healthWorker difunde NVR_OFFLINE y HDD_FULL con nombre del NVR y uso de disco (healthWorker.ts:168-178, 227-230). Las reciben OPERATOR y AUDITOR sin permiso sobre ese NVR, aunque access-policy define HDD y estado del NVR como recursos de todo el dispositivo, sólo para privilegiados o permisos NVR-scoped (access-policy.ts:37-58).
- MEDIO. El permiso NVR-scoped se aplica distinto según la ruta. cameras.ts (userCanAccessCamera) y getViewableCameraIds sólo consideran filas camera-scoped (cameras.ts:41-46; camera-scope.ts:117-123). hls-auth y access-policy aceptan filas NVR-scoped (access-policy.ts:66-79). Resultado: un usuario con canView sobre todo un NVR puede pedir HLS de todos sus canales, pero /api/cameras no le muestra cámaras y start-stream le responde 403.
- MEDIO. canHighQuality no se exige fuera de la vía nativa. hls-auth autoriza cualquier tipo de path (_main, _main_h264) sólo con canView (hlsAuth.ts:42-48, 93-100), y POST /api/cameras/:id/start-stream con streamType main o main_h264 sólo exige canView (cameras.ts:368-384). La vía nativa sí lo exige (native-readiness.ts:77-82).
- MEDIO. Los snapshots de analítica son públicos. Se guardan en /uploads/analytics/YYYYMM/<id de 96 bits>.jpg (analytics.ts:244-255), y /uploads/ se sirve sin autenticación (server.ts:233-237) con Cache-Control public (nginx.conf:88-97). Cualquiera que obtenga la URL los ve, y el acceso no se puede revocar por permiso de cámara.
- MEDIO. No hay protección del último ADMIN ni contra la auto-degradación. PUT /api/users/:id deja que un ADMIN se quite el rol o se desactive (users.ts:221-258). La web sólo deshabilita el botón Activar/Desactivar propio (UsersPage.tsx:509). El selector de rol no se bloquea para uno mismo (UsersPage.tsx:565-573).
- MEDIO. El step-up no se pide en todas las acciones sensibles y no está ligado a una acción. No lo exigen crear un ADMIN, elevar a ADMIN, fijar la contraseña de otro, desbloquear, cambiar permisos ni mutar usuarios del NVR (users.ts:173, 222, 440, 534; nvr.ts:1561-1643). El token sirve 5 min para cualquier acción (plugins/auth.ts:144-146; auth.ts:411).
- MEDIO. Revocar o cerrar sesiones no corta el acceso. Borrar filas de Session (logout parcial, DELETE /api/auth/sessions*, DELETE /api/users/:id/sessions, reset-2fa, cambio o reset de contraseña) no invalida los JWT ya emitidos, porque authenticate no consulta Session. Tampoco revoca los grants de medios, salvo logout y cambio de permisos (auth.ts:564-596; users.ts:527, 569-571; profile.ts:98; auth.ts:527, 898).
