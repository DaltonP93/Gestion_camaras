## Hallazgos de RBAC y exposición (sin consolidar; ver la matriz principal)

- [PLAUSIBLE, alta] Saltar el MFA con tokens intermedios: server.authenticate sólo verifica firma y vencimiento del JWT (plugins/auth.ts:77-81) y no mira el claim 'step'. El tempToken {sub, step:'2fa'} se firma con el mismo secreto y se devuelve en el body del login tras una contraseña correcta, antes del segundo factor (auth.ts:162-168); el enrollToken {step:'mfa-enroll'} dura 15 min (auth.ts:152-159). Enviado como 'Authorization: Bearer' pasa todas las rutas con authenticate, y la CSRF no aplica a Bearer (lib/csrf.ts:37-39). Con role=undefined, userCanAccessCamera usa los UserPermission del sub (cameras.ts:37-46): con sólo la contraseña se accede a stream, snapshot y PTZ de las cámaras permitidas, a /api/profile, /api/auth/change-password, /api/alerts y /api/views (cameras.ts:118, 316, 337, 357). authorize([...]) sí lo rechaza (rol undefined). No ejecutado.
- [PLAUSIBLE, alta] El refresh JWT sirve como access token: lleva sub/username/role, dura 7 días y se firma con el mismo secreto (auth.ts:967-977, 631-635). Como authorize sólo verifica firma y rol (plugins/auth.ts:99-106), funciona como Bearer en cualquier ruta del rol y no lo frenan ni sessionTimeoutMinutes ni borrar la Session (cerrar sesión, cambiar contraseña, revocar como admin). Sólo se obtiene de la cookie HttpOnly (Path=/api/auth), pero si se filtra, revocarla no corta el acceso. No ejecutado.
- [CONFIRMADO por lectura] Cambios de rol y de estado sobre tokens ya emitidos: authorize toma el rol del JWT (plugins/auth.ts:103-106) y PUT /api/users/:id cambia role/active/password sin revocar sesiones ni tokens (users.ts:222-258; sólo corta WS si active=false). Un ADMIN degradado conserva ADMIN hasta que vence su access token (sessionTimeoutMinutes, hasta 1440: security-policy.ts:35); el propio código lo reconoce en auth.ts:939-941. Además el cambio a ADMIN no pide step-up (DELETE sí: users.ts:262) y la auditoría USER_UPDATED no guarda qué cambió (users.ts:252).
- [PLAUSIBLE, alta] XSS almacenado en el mismo origen vía branding: POST /api/appearance/upload valida el MIME declarado por el cliente (appearance.ts:133-136, 175) y toma la extensión del nombre de archivo del cliente (appearance.ts:184-186). Un archivo declarado image/png con nombre .html o .js se guarda así en UPLOADS_DIR/branding (appearance.ts:196-198), y @fastify/static lo sirve por extensión en /uploads/ del mismo origen (server.ts:233-237; nginx.conf:88-97). La CSP de la API permite script-src 'self' (security-headers.ts:28), así que un .html subido puede cargar un .js subido y llamar a /api/* con las cookies de un ADMIN (la CSRF acepta mismo origen). Además .svgz no lo cubre el bloqueo de SVG (appearance-policy.ts:36-41). Lo puede hacer cualquier usuario con canManageAppearance, no sólo ADMIN (appearance.ts:68-88). No ejecutado.
- [PLAUSIBLE, media] Apariencia global controlada por un no ADMIN: customCss (hasta 10000 caracteres) y URL externas de logo/favicon (appearance.ts:17-21, 36-39) se aplican a todas las sesiones y a la pantalla pública de login (GET público, appearance.ts:90-116; appearanceTokens.ts:469-476). El SPA no tiene CSP (nginx-spa.conf sin Content-Security-Policy; la CSP de helmet sólo cubre respuestas de la API). El input de contraseña del login es controlado (LoginPage.tsx:63-65), lo que en React refleja el valor como atributo y permite exfiltrar por selectores CSS hacia un host externo. siteName se inserta sin escapar en el HTML del correo de recuperación (auth.ts:790-799). No ejecutado.
